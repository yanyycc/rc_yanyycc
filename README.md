# HTTP 通知服务 MVP

接收业务系统提供的 HTTP 请求，先写入 SQLite，再由独立 Worker 异步投递。供应商短暂故障时有限重试，进程中断后通过租约回收任务。

```text
业务系统 → FastAPI → SQLite 任务表 ← Worker → 外部 HTTP(S) API
                          ↑           |
                          └── 投递结果 ┘
```

当前实现包含：参数校验、内部令牌鉴权、提交去重、持久化接收、并发投递、退避重试、租约恢复、状态和逐次尝试查询、健康检查、本地示例与故障测试。

## 快速启动（Windows PowerShell）

要求 Python 3.11 或更高版本。本次在 Windows、Python 3.14.5 上验证。所有命令从项目根目录运行。

### 1. 安装

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-lock.txt
.\.venv\Scripts\python.exe -m pip install -e ".[test]"
```

`requirements-lock.txt` 记录本次测试的依赖版本；`pyproject.toml` 定义允许范围。锁文件不包含本地路径或业务凭据。Linux/macOS 对应解释器为 `.venv/bin/python`，环境变量使用 `export NAME=value`。

### 2. 配置与初始化

在运行 API、Worker 和示例的各终端中设置相同环境变量；令牌示例仅供本地演示，生产请替换：

```powershell
$env:INTERNAL_API_TOKEN = 'local-demo-token-change-me'
$env:DATABASE_PATH = Join-Path $PWD 'data/notifications.db'
$env:ALLOWED_ORIGINS = 'http://127.0.0.1:9001'
```

首次运行时初始化数据库：

```powershell
.\.venv\Scripts\python.exe -m notification_service.storage
```

这是独立初始化命令，重复运行不会清空任务。API/Worker 不自动修改 schema。配置项见 [.env.example](.env.example)，它只是示例，不会被程序自动加载。

### 3. 分别启动三个进程

终端 A：本地模拟供应商。

```powershell
.\.venv\Scripts\python.exe -m uvicorn examples.mock_supplier:app --host 127.0.0.1 --port 9001 --no-access-log
```

终端 B：API，设置上面的环境变量后运行。

```powershell
.\.venv\Scripts\python.exe -m uvicorn notification_service.api:create_app --factory --host 127.0.0.1 --port 8000 --no-access-log
```

终端 C：Worker，设置相同环境变量后运行。

```powershell
.\.venv\Scripts\python.exe -m notification_service.worker
```

API 与 Worker 必须使用同一个数据库绝对路径。默认部署为单机、一个 Worker 进程；每个进程内并发五个请求。Ctrl+C 停止时 Worker 停止领取并有限等待在途任务，强制退出由租约恢复兜底。

### 4. 提交并观察

在另一个已设置内部令牌的终端运行：

```powershell
.\.venv\Scripts\python.exe examples/submit_notification.py --mode flaky --key demo-flaky-001
```

模拟供应商对同一个示例事件前两次返回 503，第三次返回 204。脚本输出任务状态和投递记录。再次使用同一参数和 key 执行，会查询原任务，不创建新任务。

其他模式：`success` 立即 204；`bad` 返回 400，不重试；`slow` 等待 15 秒，超过默认总时限，最多尝试五次。使用不同模式时换一个 key；相同 key 不同内容按协议返回 409。

## API 协议

除 `/health/live` 外均需 `Authorization: Bearer <INTERNAL_API_TOKEN>`。入站媒体类型为 `application/json`，不支持压缩请求体。完整协议见 [需求分析与系统设计](docs/需求分析与系统设计.md)。

| 方法与路径 | 用途 |
|---|---|
| `POST /v1/notifications` | 创建通知，必须提供 Idempotency-Key |
| `GET /v1/notifications/{id}` | 查询状态与最近结果 |
| `GET /v1/notifications/{id}/attempts` | 查询按序排列的尝试历史 |
| `GET /health/live` | API 进程存活 |
| `GET /health/ready` | 数据库与 schema 就绪；不代表 Worker 正常 |

提交示例：

```json
{
  "url": "http://127.0.0.1:9001/success",
  "method": "POST",
  "headers": {"Content-Type": "application/json"},
  "body": "{\"event\":\"paid\",\"contact_id\":\"c_123\"}"
}
```

`body` 是原始 UTF-8 文本，服务不重新序列化其内部 JSON。支持 POST/PUT/PATCH/DELETE；URL 必须匹配管理员允许的 origin。Header 值限 ASCII，禁止传输控制 Header、控制字符及重复名称。限制：入站 1 MiB、Body 256 KiB、最多 32 个 Header 且名称和值合计 16 KiB。

首次创建返回 202 和任务 ID；同一 key 同一内容返回 200 与原 ID；同一 key 不同内容返回 409。幂等键在 MVP 服务范围内全局唯一，各业务系统应自行增加业务前缀。Header 名称大小写和外层 JSON 字段顺序不影响去重，Body 文本变化会影响。

非法 JSON 400、鉴权失败 401、不存在 404、入站超限 413、媒体类型不支持 415、字段校验失败 422、数据库暂不可用 503。失败响应统一为 `{"error":{"code":"...","message":"...","details":[]}}`，不回显秘密输入。无效 UUID 返回 422。API 暂不暴露 Swagger 页面，协议以设计文档为准。

## 投递与故障行为

```text
pending → processing → succeeded
              ↓
          retry_wait → processing
              或
            failed
```

- 接收成功只表示任务已持久化，不表示供应商已经收到。
- HTTP 2xx 表示送达成功；不读取响应 Body，不判断供应商业务状态，不自动跟随 3xx。
- 408、429、5xx、临时网络异常和超时重试；其他 4xx、3xx、TLS 验证失败、被移出允许列表的目标直接失败。
- 五次尝试包含首次；失败间隔为 5、10、20、40 秒并附加 ±20% 抖动。429/503 的 Retry-After 支持秒数和日期，按设计基线最多采用 3600 秒。
- 单次总超时 10 秒、连接超时 3 秒、租约 30 秒、轮询 1 秒。配置须满足租约大于总超时加数据库等待预算。
- 领取和尝试记录在同一事务提交；网络调用不持有数据库事务。写回验证 lease_token 和租约有效期，过期执行者无法覆盖后续结果。
- 领取即占用一次尝试；租约过期记 interrupted，并立即恢复为可领取状态或在次数耗尽后失败。领取后尚未发送就退出，也占用一次尝试。
- 结果写回失败不触发内存中的直接重发，保留 processing 等待租约回收。

SQLite 使用 WAL、FULL 同步、外键和有限写锁等待；每次数据库操作在同一线程内完成连接使用与事务。数据库完整且进程恢复运行的前提下，已确认任务可以继续处理；不承诺单机磁盘损坏后的零丢失。

## 边界与已知限制

- 超时可能意味着对方已经执行；恢复和重试可能重复投递。提交去重不等于供应商幂等。
- 不保证顺序、恰好执行一次或永久故障下必达；failed 不等于确定没有产生外部副作用。
- 没有人工重放、取消、Worker 状态 API、任务分页列表、调用方隔离、入站限流、队列容量限制或自动清理。Worker 有结构化心跳日志；需关注积压和磁盘空间。
- 五次重试仅适合演示初始策略，不能覆盖供应商长时间停机；相关改进已列入后续清单。
- 静态供应商凭据保存在数据库中，无字段加密或自动刷新；需保护数据库文件、WAL 和备份，不使用真实敏感数据进行未加固的演示。
- 允许列表为精确 origin，不是完整 DNS 重绑定防护。生产需要 HTTPS 入口、可信供应商和出站网络策略；本示例仅监听本机，不作为生产部署方案。
- HTTP 客户端不继承环境代理配置、不关闭 TLS 校验、不打印请求 Header/Body。运行 API 时按示例禁用访问日志，避免 URL 参数进入日志。
- 消息队列、低延迟唤醒、分组顺序与单次投递模式只在 [后续版本改进清单](docs/后续版本改进清单.md) 中规划，未实现。

## 测试

```powershell
.\.venv\Scripts\python.exe scripts/run_tests.py -q
```

测试脚本为每次运行创建独立的工作区临时目录，避免依赖系统临时目录权限。临时产物在 `.test-tmp/`，不会提交 Git。

测试包含 API/数据库集成、并发去重、原子领取、错误分类、总超时、Retry-After、租约恢复与旧执行者写回防护，以及真实本地 HTTP 与强制进程中断：

- API 确认 202 后强制结束再重启，任务仍保留。
- Worker 领取后发送前被结束，租约过期后恢复。
- 供应商已经产生副作用而 Worker 被结束，再次执行展示重复风险。
- 真实 503 后成功、400 终止、302 不跳转、超时五次终止。

测试只访问回环地址和内存模拟目标，不调用真实供应商。它们证明所覆盖的功能和进程故障场景，不代表吞吐 SLA、断电恢复或生产容灾认证。

## 代码结构与设计取舍

```text
src/notification_service/
  api.py          接收、鉴权、查询与安全错误映射
  config.py       配置和 origin 规范化
  protocol.py     输入模型、Header/URL 约束与请求摘要
  storage.py      schema v1、短事务、领取、回收和写回
  delivery.py     HTTP 投递、错误分类和退避策略
  worker.py       有限并发、轮询、日志和进程入口
tests/            API、数据库、投递及真实进程测试
examples/         模拟供应商和提交查询脚本
docs/             设计、后续规划及 AI 使用说明
```

系统按六个核心模块组织。状态和事务集中于 storage，协议与重试逻辑可独立测试。schema v1 内置于 storage，由独立初始化命令管理；未来发生 schema 变更时再引入逐版本迁移。

数据库任务表让接收和持久化在单个事务完成，降低部署成本和双写复杂度，适合当前单机范围，未来根据瓶颈再演进。

| 选择 | 当前采用的原因 | 可替代方案与适用条件 |
|---|---|---|
| FastAPI | 用于异步接收、参数处理、鉴权依赖和统一错误响应 | Flask 等框架也能承载接口，需要相应组织参数校验和并发执行 |
| SQLite 任务表 | 本地启动依赖少，接收和持久化可以使用同一事务 | PostgreSQL 适合多机部署和更高写入并发；引入 MQ 时还需明确任务存储与分发的一致性 |
| HTTPX | 提供异步请求、连接池、超时和流式响应控制 | 标准库 HTTP 客户端配合线程池也可实现，需要自行管理并发和超时边界 |
| 独立 Worker + 持久化到期时间 | 投递与接收分离，重启后可继续查询和执行任务 | Celery 等任务框架可承担更多调度功能，同时增加 Broker 配置与运维成本 |

## 后续扩展方向与设计

以下列出后续版本候选方案；当前交付范围保持本 README 所述 MVP。已有连接池和超时机制继续复用，新增调度、隔离和容灾能力按瓶颈逐步加入。

| 场景 | 要做什么 | 可以如何设计 | 验证重点 |
|---|---|---|---|
| 瞬时大量请求 | 控制入站、缓冲峰值、提高处理能力 | 调用方限流与队列水位；按供应商限制并发；写入成为瓶颈时迁移 PostgreSQL；需要独立分发时采用任务表 + Outbox + 持久化 MQ，再扩容 Worker | 已接收任务可追踪，超限明确拒绝，峰值结束后积压能够消退 |
| 首次转发延迟更低 | 减少固定轮询等待 | 持久化提交后立即唤醒 Worker，保留扫描兜底；多机时评估 MQ/CDC；按 next_attempt_at 调度重试；分别测量接收、排队和外部调用延迟 | 调度 P95/P99 改善，唤醒丢失后任务仍能执行 |
| 端到端一致性与持久性 | 覆盖业务提交、通知接收和队列分发的故障窗口 | 业务方同事务写业务数据与 Outbox；通知服务原键去重；使用 MQ 时发布确认、消费确认与持久化调度配合；增加对账、复制、备份和恢复演练 | 明确 RPO/RTO，对每个确认边界注入故障，核对已接收任务 |
| 部分消息要求有序 | 按业务范围保持顺序 | 引入 ordering_key 与业务序号，同组串行、不同组并行；前序失败阻塞后序；维护组游标并处理缺号；业务生效顺序需要供应商协议配合 | 组内重试不越序，其他组可继续处理 |
| 供应商不幂等且最多投递一次 | 为这类消息提供单次策略 | 发送前原子消费一次资格，禁止请求级自动重试；结果未知时停止并核查 | 重复消费、进程恢复不会再次发送；明确接受发送前崩溃造成的漏发 |
| 长期故障与日常运维 | 增加可发现、可恢复的失败处理 | 设置合理重试期限；记录 Worker 心跳与积压指标；失败告警；受鉴权和审计保护的重放；按调用方隔离幂等键和任务访问 | 能发现停滞任务，恢复操作可审计且不会无意重复执行 |

几个扩展约束需要持续保留：

- MQ 缓冲峰值仍受存储、消费者和供应商吞吐限制；采用任务库作为事实来源时，也需要评估数据库入站写入能力。
- 降低延迟时，接收成功仍以持久化提交为前提；唤醒通知只负责加速发现任务。
- 有序需约定是发送顺序还是业务生效顺序，供应商异步处理时两者可能不同。
- 对不支持幂等或可靠事务协议的供应商，“最多尝试一次”需要接受可能漏发。若要求业务恰好执行一次，必须获得供应商配合。

建议顺序：先明确容量与延迟指标、顺序语义和容灾目标，再补观测及背压，然后依据测量结果扩展调度和基础设施。详细分项和验收规划见 [后续版本改进清单](docs/后续版本改进清单.md)。

2. 按快速启动说明运行一遍演示，确认能解释重试、租约、重复投递和终止失败的取舍。
3. 仓库采用 `rc_yanyycc`，源码、文档、依赖配置和测试纳入版本管理；`.gitignore` 排除虚拟环境、数据库、临时测试产物和真实凭据。正式提交时确保评审者具有私有仓库访问权限。
4. 推送后从干净克隆安装、运行测试和示例，再提交仓库链接。

作业要求 MVP 并允许明确系统边界。后续扩展清单中的容量、顺序和容灾能力可作为工程演进说明，当前无需为提交一次性实现。
