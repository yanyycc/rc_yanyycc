# HTTP 通知服务：需求分析与系统设计

版本：v0.1 MVP，2026-09-06。

状态：当前 MVP 已实现，启动和验证方式见 [README](../README.md)。本文记录第一版约定，后续清单不属于已实现能力。Python 已由用户确认；技术实现细节由 AI 按用户授权完成。

## 1. 作业目标与交付物

原始需求：构建一个内部服务，接收多个业务系统提交的外部 HTTP(S) 通知请求，并尽可能可靠地投递。不同供应商的 URL、Header 和 Body 不同，业务系统无需同步等待或消费供应商的响应。

最终提交到 `rc_{your_nickname}` GitHub 仓库，包含：

1. 可运行的 Python MVP。
2. README：启动方式、配置、示例请求、测试方式。
3. 设计文档：系统边界、架构、投递语义、失败处理、取舍及演进。
4. AI 使用说明：实际协助内容、未采纳建议和用户作出的关键判断。开发时持续记录，不虚构历史。

本地测试覆盖接收、投递及进程中断恢复；不宣称生产容灾、磁盘损坏恢复或吞吐 SLA。

## 2. 系统定位与边界

```text
业务系统 --HTTP JSON--> 接收 API --事务写入--> SQLite
                                             ↑ ↓
                                       投递 Worker
                                             |
                                        HTTP(S) 请求
                                             ↓
                                         外部供应商
```

第一版是通用 HTTP 投递服务。业务方负责确定目标、组装供应商需要的请求，并提供必要鉴权 Header；通知服务保存和发送这些信息，管理超时、重试、状态及恢复。

### 2.1 负责的问题

- 请求合法性检查与内部调用鉴权。
- 接收任务时先持久化，再返回接收成功。
- 调用方重复提交去重。
- 后台投递、有限重试、投递过程记录。
- Worker 中断后的任务回收。
- 查询任务状态和尝试记录。
- 限定可访问的供应商目标，避免成为任意网络代理。

### 2.2 第一版不负责的问题

| 不实现项 | 原因及边界 |
|---|---|
| 供应商业务字段转换 | 由业务方提交完整请求，避免扩展为集成平台 |
| 供应商 OAuth 刷新、动态签名计算 | 涉及供应商专属逻辑；第一版使用提交的静态 Header。短期凭据可能在重试前失效，此类集成需另行适配 |
| 解析响应 Body 中的业务结果 | 第一版统一以 HTTP 2xx 为投递成功；200 中携带业务错误无法自动识别 |
| 恰好一次业务执行 | 请求可能已经被处理，但响应丢失；单靠发送端无法消除重复副作用 |
| 严格顺序 | 并发、失败重试可能造成乱序 |
| 业务提交与通知提交的跨服务原子性 | 本服务负责持久化接收后的任务；提交前的丢失需要业务方 Outbox 等机制解决 |
| 无限重试、永久不可用目标的必达 | 重试耗尽后明确失败并保留记录 |
| 管理页面、多租户平台、多机高可用 | 作业第一版通过 API 和日志操作，单机部署 |
| 二进制上传、流式请求、超大文件 | 第一版 Body 为 UTF-8 文本，覆盖 JSON、XML、表单文本等常见通知 |
| 自动回调业务系统、取消及人工重放接口 | 不属于最小闭环；查询足以获知结果，人工重放后续单独设计权限和去重语义 |

## 3. 功能清单与验收要求

以下 F01–F10 均已实现，验收测试在 tests 中。

| 编号 | 功能 | 具体要求 | 验收方式 |
|---|---|---|---|
| F01 | 接收通知 | 校验鉴权、幂等键、方法、URL、Header 和 Body；事务提交成功后返回任务 ID | 有效请求返回 202；非法请求不创建任务；数据库不可写时不能返回接收成功 |
| F02 | 提交去重 | 相同幂等键及相同请求返回同一任务；相同键不同内容返回 409 | 顺序和并发重复提交均只有一条任务；不因重提而重置已失败或成功任务 |
| F03 | 持久化 | 保存目标请求、状态、尝试次数、下次执行时间及时间戳 | API/Worker 重启后，已确认接收的任务仍能查询和继续处理 |
| F04 | 异步投递 | Worker 领取到期任务并发送；API 不等待外部响应；控制并发和总超时 | 模拟供应商慢响应时，接收接口仍先完成任务入库；Worker 不无限占用资源 |
| F05 | 成功判断 | 外部返回 200–299 即成功；不解释业务 Body；不自动跟随重定向 | 204 标记成功；302 不访问 Location；200 携带业务失败文本仍按协议标记成功 |
| F06 | 失败与重试 | 临时网络失败、超时、408、429、5xx 按退避策略重试；其余失败分类终止 | 用可控模拟端点测试 500 后 200、连续超时、400、429 和重试耗尽 |
| F07 | 中断恢复 | 领取任务时设置租约；过期租约可回收；旧执行者不能覆盖新状态 | 领取后或发送中强制结束 Worker，再启动能够回收；过期执行结果被拒绝写回 |
| F08 | 状态查询 | 返回任务状态、尝试次数、时间、最近错误，不返回秘密 Header 或请求 Body | 查询已有任务为 200，不存在为 404；响应不泄露凭据 |
| F09 | 尝试记录 | 记录每次尝试的起止时间、结果、状态码、耗时和安全错误摘要 | 可以复原失败后成功的过程；不把一次失败覆盖得无迹可查 |
| F10 | 运行支持 | 提供配置、结构化日志、存活/就绪检查、启动和测试说明 | 按 README 可启动 API、Worker、模拟供应商并演示完整流程 |

## 4. 输入输出协议

### 4.1 通用约定

- 业务系统到本服务：HTTP/1.1 兼容的 REST API，JSON，UTF-8；生产部署入口使用 HTTPS，本地允许 HTTP。
- API 路径统一为 `/v1`；健康检查不带版本。
- 鉴权：除存活检查外，使用 `Authorization: Bearer <INTERNAL_API_TOKEN>`。第一版为共享内部服务令牌，不支持用户级隔离。
- 时间：UTC RFC 3339，例如 `2026-09-06T09:30:00Z`。
- 任务 ID 和尝试 ID：UUID 字符串。
- 所有业务响应使用 `application/json`。示例中的 ID 和时间仅为说明。
- API 入站请求体最多 1 MiB，按实际读取字节限制，不能只信任 Content-Length。
- 拒绝未声明字段，避免输入拼写错误被静默忽略。

### 4.2 创建通知：`POST /v1/notifications`

请求 Header：

```http
Authorization: Bearer <INTERNAL_API_TOKEN>
Idempotency-Key: payment-20260906-0001-crm
Content-Type: application/json
```

请求 Body：

```json
{
  "url": "https://crm.example.com/api/contacts/update",
  "method": "POST",
  "headers": {
    "Authorization": "Bearer supplier-token",
    "Content-Type": "application/json"
  },
  "body": "{\"contact_id\":\"c_123\",\"status\":\"paid\"}"
}
```

注意：外层 JSON 是本服务协议；其中 `body` 是待发送的原始文本，不是嵌套 JSON 对象。本服务将其 UTF-8 编码直接发送，不重新序列化内部 JSON，以免改变格式或签名输入。

| 字段 | 类型 | 要求 |
|---|---|---|
| `Idempotency-Key` | HTTP Header 字符串 | 必填，1–128 个可打印 ASCII 字符；建议包含业务事件和目标。第一版在整个服务内唯一 |
| `url` | string | 必填，完整 HTTP(S) URL，最长 2048 字符；禁止 URL 用户名/密码、fragment；目标必须命中管理员配置的允许列表 |
| `method` | string | 必填，大写 `POST`、`PUT`、`PATCH` 或 `DELETE`；其他方法暂不支持 |
| `headers` | object<string,string> | 可选，默认 `{}`；最多 32 项，UTF-8 编码后的名称和值合计不超过 16 KiB；名称按 HTTP token 校验，值禁止 CR/LF |
| `body` | string | 可选，默认空字符串；UTF-8 编码后最多 256 KiB；不支持 null、对象或数组 |

额外规则：

- 禁止调用方设置 `Host`、`Content-Length`、`Transfer-Encoding`、`Connection`、`Keep-Alive`、`TE`、`Trailer`、`Upgrade`、`Proxy-Authorization`、`Proxy-Connection`；由 HTTP 客户端控制传输字段。
- Header 名称大小写不敏感；拒绝大小写不同但名称重复的输入。值限 ASCII，禁止除水平制表符外的控制字符及首尾空白，避免接收无法通过 HTTP 客户端发送的内容。
- 非空 Body 必须提供 `Content-Type`；不校验内部文本是否符合该媒体类型。
- 本服务的内部鉴权 Header 不会自动转发。只发送请求 JSON 中的供应商 Header，以及 HTTP 客户端必要的传输 Header。
- 不自动把内部幂等键发送给供应商；业务方应在供应商明确支持时提供对应幂等字段。内部去重与供应商业务幂等是两个不同机制。

首次成功接收返回 `202 Accepted`，包含 `Location: /v1/notifications/<id>`：

```json
{
  "id": "7eef66e7-7d9b-4c67-b944-4edda0ad7768",
  "status": "pending",
  "deduplicated": false,
  "created_at": "2026-09-06T09:30:00Z"
}
```

相同幂等键和相同请求重提：返回 `200 OK`，同一 ID、当前状态、原创建时间和 `deduplicated: true`，不再创建或调度任务。相同键不同请求：返回 `409 Conflict`。

去重比较：对校验后填入默认值的请求建立确定性表示；Header 名称转小写并按名称排序；URL、方法、Header 值和 Body 文本按内容比较。外层 JSON 字段顺序不影响结果，Body 内部空白或字段顺序变化视为不同内容。数据库唯一约束负责并发正确性。

### 4.3 查询任务：`GET /v1/notifications/{id}`

成功返回 `200 OK`：

```json
{
  "id": "7eef66e7-7d9b-4c67-b944-4edda0ad7768",
  "status": "retry_wait",
  "attempt_count": 2,
  "max_attempts": 5,
  "next_attempt_at": "2026-09-06T09:31:10Z",
  "last_http_status": 503,
  "last_error": {
    "code": "upstream_server_error",
    "message": "Upstream returned HTTP 503"
  },
  "created_at": "2026-09-06T09:30:00Z",
  "updated_at": "2026-09-06T09:30:50Z",
  "completed_at": null
}
```

- `status` 为第 5 节定义的枚举。
- `next_attempt_at` 只在 `pending`、`retry_wait` 时有值，其他状态为 null。
- 从未获得 HTTP 响应时，`last_http_status` 为 null；最新一次尝试没有 HTTP 响应时亦为 null，不能沿用旧状态码误导调用方。
- 最新尝试成功后 `last_error` 为 null；历史错误保留在尝试记录中。
- `completed_at` 仅终态有值。请求详情、供应商响应 Body 和完整 URL 不对查询接口返回。

### 4.4 查询尝试：`GET /v1/notifications/{id}/attempts`

返回 `200 OK`，`items` 按 `attempt_number` 升序。第一版最多五次，不需要分页：

```json
{
  "notification_id": "7eef66e7-7d9b-4c67-b944-4edda0ad7768",
  "items": [
    {
      "id": "8dceea92-8ba5-4cc0-8d29-4ed9a2c506f5",
      "attempt_number": 1,
      "outcome": "retryable_failure",
      "started_at": "2026-09-06T09:30:01Z",
      "finished_at": "2026-09-06T09:30:02Z",
      "duration_ms": 1000,
      "http_status": 503,
      "error_code": "upstream_server_error",
      "error_message": "Upstream returned HTTP 503"
    }
  ]
}
```

`outcome`：`running`、`succeeded`、`retryable_failure`、`permanent_failure`、`interrupted`。运行中结束时间与耗时为 null；崩溃后无法得知真实结束时间时，耗时仍为 null，结束时间记录发现租约过期的时间。空历史返回空数组，不存在的任务返回 404。

### 4.5 错误响应

统一结构，不原样回显秘密输入或异常堆栈：

```json
{
  "error": {
    "code": "idempotency_conflict",
    "message": "Idempotency key is already used for a different request",
    "details": []
  }
}
```

| HTTP 状态 | 场景 |
|---|---|
| 400 | 无法解析的 JSON |
| 401 | 内部令牌缺失或不正确 |
| 404 | 查询的任务不存在 |
| 409 | 幂等键与已有请求内容冲突 |
| 413 | API 入站请求体超过 1 MiB |
| 415 | 接收 API 的媒体类型不是 application/json |
| 422 | 字段、Body 大小、URL、Header 或幂等键校验失败 |
| 503 | 数据库暂时不可用或写锁等待超时，任务未确认接收 |
| 500 | 未分类内部故障；调用方使用原幂等键重试以消除接收结果不确定性 |

供应商返回 400/500 不会直接成为创建任务接口的返回码；其结果体现在任务状态中。

### 4.6 健康检查

- `GET /health/live`：无需鉴权，进程能够响应即返回 `200 {"status":"ok"}`。
- `GET /health/ready`：需要内部鉴权，数据库可连接且 schema 已初始化返回 `200 {"status":"ready"}`，否则 503。只表示 API 就绪，不表示 Worker 正常。
- Worker 使用启动、周期心跳和失败日志报告状态；第一版不提供完整监控平台。

## 5. 投递语义与状态机

### 5.1 可靠性承诺

采用允许重复的异步投递与有限重试。通常称为“至少一次投递方向的设计”，但重试存在上限，因此不能宣称每个任务一定被供应商成功接收一次。

准确承诺是：已持久化并确认接收的任务不会仅因 API/Worker 进程重启而消失；在数据库文件完好、服务恢复运行的前提下继续处理，直到成功或明确失败。磁盘损坏、主机丢失和永久停机不在单机 MVP 的保障范围内。

若供应商已处理请求但响应丢失，或 Worker 在发送后、记录成功前退出，恢复后可能重复发送。供应商需要支持幂等才能避免重复业务副作用。

### 5.2 状态迁移

```text
pending ──领取──> processing ──2xx──> succeeded
                    |
                    ├──可重试失败且剩余次数──> retry_wait ──到期领取──> processing
                    |
                    ├──永久失败/次数耗尽──> failed
                    |
                    └──租约过期──> retry_wait 或 failed（次数耗尽）
```

- `pending`：已持久化，等待首次执行。
- `processing`：已领取，本次尝试正在执行。
- `retry_wait`：等待下次尝试。
- `succeeded`、`failed`：终态，不因重复提交而重新执行。

### 5.3 第一版执行参数

这些是作业 MVP 的初始默认值，不是从题目中推导出的业务 SLA。参数集中配置，新任务保存创建时的 `max_attempts`。

| 参数 | 初始约定 |
|---|---|
| 最大尝试次数 | 5，包含首次；领取一次计一次，即使随后进程退出 |
| 单次总时限 | 10 秒，使用总时限包裹完整网络操作，不能仅依赖分阶段超时 |
| 连接超时 | 3 秒，仍受总时限约束 |
| 第 n 次失败后的退避 | `min(5 × 2^(n-1), 300)` 秒，再乘 0.8–1.2 随机抖动；n 从 1 起 |
| Retry-After | 对 429、503 支持秒数或 HTTP 日期；取与退避值较大者，服务端提示等待最多采用 3600 秒；无效值忽略 |
| Worker 轮询 | 1 秒 |
| 并发投递数 | 5；只领取空闲执行槽位可立即运行的任务 |
| 领取租约 | 30 秒，大于单次总时限；第一版不续租 |
| 自动重定向 | 禁止 |
| 供应商响应 Body | 不保存、不解析；以流式方式读取响应头后关闭，避免下载无限响应内容 |

### 5.4 失败分类

| 结果 | 行为 |
|---|---|
| HTTP 2xx | 成功 |
| HTTP 408、429、5xx | 剩余次数充足则重试 |
| HTTP 3xx、其他 4xx | 终止失败；不跟随跳转 |
| 临时 DNS 错误、连接拒绝/重置、连接或读取超时 | 剩余次数充足则重试 |
| TLS 证书验证失败、目标不再允许、请求构造错误 | 终止失败，不关闭 TLS 校验绕过问题 |
| Worker 租约过期 | 本次标为 interrupted；有剩余次数则重试，否则失败 |

终止失败需要记录具体原因，如 `attempts_exhausted`、`upstream_client_error`、`target_not_allowed`，不能只留一个无上下文的 failed。

## 6. 数据与并发设计

采用本地 SQLite 任务表作为持久化队列，API 与一个独立 Worker 进程共享数据库文件。开启外键、WAL 和 synchronous=FULL；默认写锁等待 2 秒。仅用于单机本地磁盘，不使用共享网络文件系统。

### 6.1 notifications 表

| 字段组 | 内容 |
|---|---|
| 身份与去重 | id、唯一 idempotency_key、request_hash |
| 待发请求 | url、method、headers_json、body_text |
| 调度 | status、attempt_count、max_attempts、next_attempt_at |
| 领取保护 | lease_token、lease_expires_at |
| 最近结果 | last_http_status、last_error_code、last_error_message |
| 时间 | created_at、updated_at、completed_at |

索引：幂等键唯一索引；`(status, next_attempt_at)`；`(status, lease_expires_at)`。

### 6.2 delivery_attempts 表

字段：id、notification_id、attempt_number、lease_token、outcome、started_at、finished_at、duration_ms、http_status、error_code、error_message。`(notification_id, attempt_number)` 唯一，notification_id 为外键。

### 6.3 关键事务

1. 接收事务：写任务；唯一键冲突时读取已有记录并比较内容，返回去重结果或 409。
2. 领取事务：在短写事务中检查到期条件，更新 processing、次数和租约，同时创建 running 尝试记录。提交后才能发 HTTP。
3. 结果事务：按任务 ID、processing 状态及 lease_token 条件写回；同一事务更新尝试与任务状态。旧租约结果不允许覆盖新结果。
4. 回收事务：将过期 running 尝试标为 interrupted，按剩余次数恢复调度或进入 failed。

网络调用永远不放在数据库事务中。数据库写回失败时不把任务在内存中当成已完成；租约机制负责后续恢复，可能因此重复发送。

第一版不自动删除任务或去重键；保留期和归档是后续运营策略，避免任务删除后旧幂等键再次执行。测试数据使用独立临时数据库。

## 7. 安全与运维最低要求

- 管理员配置允许访问的精确 origin（scheme、host、port），不能由提交方修改。每次发送前重新检查，禁用自动跳转。
- 生产使用出站网络策略限制内网、元数据地址等访问；允许列表不等同于完整 DNS 重绑定防护。单机示例只连接受管理员控制的目标，本地模拟目标显式加入开发配置。
- Header 和 Body 可能包含凭据或个人数据，数据库需要操作系统文件权限保护；第一版不提供字段加密，不用于未经加固的生产敏感数据部署。
- 日志、查询与错误信息不输出 Authorization、完整请求 Body、URL 查询参数或原始客户端异常文本。
- 环境变量管理内部令牌和运行配置；`.env`、数据库、日志不得提交 Git。提供不含真实凭据的 `.env.example`。
- 结构化日志至少含 notification_id、attempt_number、outcome、http_status、duration_ms。进程退出应停止领取新任务，并给在途操作有限收尾时间；强制退出依靠租约恢复。

## 8. Python 技术方案与目录规划

技术选择：Python + FastAPI + HTTPX + SQLite + pytest。API 和 Worker 是同一代码库的两个启动入口。数据库访问使用 Python 标准库 sqlite3 和集中管理的 SQL；同步数据库调用放入线程中，每次操作的连接和整个事务始终在同一线程。schema v1 内置于 storage.py，通过独立初始化命令创建，Worker 启动检查版本，API 就绪检查版本。后续 schema 变更再增加版本迁移。

## 9. 测试与完成标准

### 必须证明的行为

1. 接收后供应商返回 204，最终 succeeded，只有一次尝试。
2. 供应商先 503 后 200，出现等待重试状态，最终成功且历史完整。
3. 持续超时最多执行五次，最终 failed，不无限重试。
4. 400 直接终止；429/503 正确解析 Retry-After；302 不跟随跳转。
5. 相同键相同内容并发提交只有一个任务；不同内容返回 409。
6. API 返回 202 后重启，任务不丢失；数据库写入失败不能返回 202。
7. Worker 领取后强制退出，租约过期后能够恢复；旧 lease_token 写回无效。
8. 模拟对方已执行但响应丢失，展示可能重复，文档与实际行为一致。
9. 非允许目标、非法 Header 和超限请求被拒绝，查询和日志无凭据泄露。

单元测试注入时钟、随机数和 HTTP 结果，避免真实等待退避。集成测试使用独立 SQLite 文件。至少保留真实本地 HTTP 和进程重启测试，不能全部通过 mock 声称恢复能力。

不预先承诺 QPS、毫秒级 SLA 或高可用性；如需性能指标，另行定义负载、硬件与测量方法。

### 实施顺序

1. 工程配置、数据库 schema 和协议模型。
2. 创建、去重和查询接口，完成接收持久化闭环。
3. Worker 领取、HTTP 投递和结果写回。
4. 重试、租约恢复和故障测试。
5. 示例、README、AI 使用说明与完整验收。

## 10. 工程依据与后续演进

专项后续规划见 [后续版本改进清单](后续版本改进清单.md)，覆盖瞬时流量、转发延迟、端到端可靠性、有序及单次投递；仅列入规划，不改变本版实现范围。

- Stripe Webhook 的官方行为展示了指数退避、有限自动重试、人工恢复以及重复和乱序的现实边界。借鉴机制，不照搬其三天重试窗口：https://docs.stripe.com/webhooks
- GitHub Webhook 文档按连接、超时、TLS 和 HTTP 错误排查投递，支持我们保存逐次尝试记录的设计：https://docs.github.com/en/webhooks/testing-and-troubleshooting-webhooks/troubleshooting-webhooks
- AWS Transactional Outbox 解决业务写入与通知发送的双写问题。业务方 Outbox 与本服务任务表是不同边界，不能用后者声称解决前者：https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html

第一版使用数据库任务表统一管理持久化和调度，降低启动和故障排查成本，满足当前作业范围。

后续按实际瓶颈演进：

| 触发条件 | 优先演进方向 |
|---|---|
| SQLite 写竞争或需要多机 Worker | PostgreSQL、数据库领取机制、正式迁移工具 |
| 扫表调度成为瓶颈或需要更大缓冲 | 评估消息队列，明确数据库与队列双写的一致性 |
| 单个供应商拖累其他目标 | 每目标并发/速率限制、隔离与熔断 |
| 供应商业务协议差异增加 | 明确的供应商适配器、凭据刷新、业务成功判定 |
| 需要人工运维 | 分页列表、受鉴权和审计保护的重放、指标与告警 |
| 需要端到端业务一致性 | 业务方 Outbox、供应商幂等契约、必要的顺序约束 |

尚需用户后续补充：截止时间、是否有指定运行环境、最终 GitHub 昵称。这些不阻碍按本基线开展本地实现。
