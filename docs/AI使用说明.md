# AI 使用说明

本项目使用 AI 辅助需求分析、方案设计、编码和测试。以下说明我在协作中作出的关键决策、AI 提供的帮助，以及方案的取舍与验证。

## 关键决策与理由

1. **先确定协议和系统边界，再开始实现。** 我要求先明确功能、输入输出及整体架构，重点区分接收成功、HTTP 投递成功与供应商业务执行成功，避免实现阶段对可靠性产生不同理解。
2. **通过故障场景审查方案。** 我要求围绕进程退出、响应丢失、重复分发和供应商超时等场景分析风险，并将一致性、持久性、有序和非幂等接口的单次投递展开为详细设计。方案明确了 Outbox 责任交接、持久化确认与恢复对账、分组序号与前序阻塞、一次性发送资格与结果未知处理，同时列出数据和协议变更、故障矩阵及验收计划。相关内容见 [故障场景与可靠性扩展设计](故障场景与可靠性扩展设计.md)，本阶段仅完成方案，不加入当前 MVP 开发。
3. **控制第一版复杂度。** 在理解 API 写入任务、Worker 轮询投递的流程后，我决定先完成当前 MVP，将瞬时流量优化、低延迟调度、有序与单次投递列入后续版本，避免同时引入多套执行语义，增加实现和验证难度。
4. **选择 Python 支持快速开发与验证。** 本次作业优先验证投递流程和故障恢复，Python 便于开发、调试和构造测试场景。

FastAPI、SQLite、HTTPX 和独立 Worker 的具体组合由 AI 提出，结合需求讨论用于本次实现。

## AI 提供的帮助

- 阅读原始 PDF，区分作业硬性要求与自行选择的 MVP 边界。
- 提出 FastAPI、SQLite 任务表、HTTPX、独立 Worker 的架构建议。
- 定义 API、幂等比较、状态机、错误分类、租约和结果写回约束。
- 检索 Stripe、GitHub、AWS、RabbitMQ、Kafka 及 SQLite 官方资料，说明工程依据和保证边界。
- 审查初版风险，指出重试窗口短、失败后缺少恢复入口、全局幂等键冲突和积压观测不足。
- 编写 MVP 代码、启动文档、本地模拟供应商，以及单元、集成和真实进程故障测试。

## 当前未采用或推迟的建议

- 独立消息队列、数据库扩容、提交后唤醒、容量控制、分组有序和单次投递模式：我要求将这些能力列入后续规划，先完成当前 MVP 的接收、投递与恢复流程。
- 风险审查中建议的多调用方鉴权、人工重放和 Worker 状态查询：当前继续遵循初版 MVP 边界，作为已知限制记录，而非宣称已经解决。
- 初版多层目录拆分：实现时按六个核心模块组织，分别封装协议、数据库事务和投递策略。
- 不采用“使用 MQ 就能让外部 HTTP 恰好执行一次”的说法；外部副作用需要供应商幂等、事务或可靠操作查询协议配合。

## 实现中的修正与验证

- 将模糊的 SQLite 同步配置明确为 WAL + FULL，并让每次事务留在同一线程中执行。
- Header 值明确限制为底层客户端可发送的 ASCII；非法编码在接收阶段拒绝。
- 连接复用时禁止自动继承先前供应商响应设置的 Cookie，避免不同通知之间产生隐式会话关联；添加了相应回归测试。
- 数据库 schema 使用独立初始化命令，API 与 Worker 启动不自动迁移。
- 测试最初受到系统临时目录权限影响，改用工作区内每次独立的临时目录；没有修改用户系统目录权限。
- 真实进程测试验证 API 重启持久化、Worker 发送前中断恢复，以及外部副作用后中断导致可能重复；不把 mock 结果当作完整可靠性证明。
