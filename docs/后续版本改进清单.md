# 后续版本改进清单

日期：2026-09-06。

状态：仅规划，全部未实现。本文不修改当前 MVP 的接口、数据库或投递行为。各项能力按实际需求和测量结果选择，不要求一次性引入全部组件。

一致性、持久性、有序和单次投递的详细事务流程、候选协议、状态与故障验收见 [故障场景与可靠性扩展设计](故障场景与可靠性扩展设计.md)。

## 1. 瞬时大量流量

当前瓶颈：SQLite 写入竞争、单 Worker 的有限处理能力、无限积压造成磁盘耗尽，以及单个慢供应商占用全部并发。

- [ ] **建立容量指标**：测量入站速率、完成速率、队列长度、最老任务年龄、数据库锁等待、磁盘余量和各供应商错误率。区分短暂突发和持续超负荷。
- [ ] **限流与背压**：按调用方限制请求速率，设置队列容量和磁盘水位；超限返回明确 429/503。未接收任务由调用方使用同一幂等键退避重提，不能返回 202 后静默丢弃。
- [ ] **供应商隔离**：每目标设置并发和速率上限；领取任务时跳过无名额的目标，防止慢目标占满全局槽位。
- [ ] **扩展存储与 Worker**：写锁或单机成为瓶颈时迁移 PostgreSQL，采用原子领取和多 Worker；扩容上限受数据库和供应商承载能力约束。
- [ ] **评估持久化消息队列**：需要更大缓冲或独立扩缩容时引入 MQ。首选保持任务数据库为事实来源，通过事务 Outbox 发布任务 ID，MQ 用于分发。不能直接“写库后顺便发 MQ”而忽略双写失败。
- [ ] **控制批量与预取**：适度批量写入/发布，消费者预取与可执行并发相匹配，避免任务被大量提前领取后空等、租约过期。
- [ ] **容量和数据保留策略**：归档终态历史、清理敏感请求内容，单独保留去重记录；清理期限不得短于约定的去重与重放期限。

权衡：队列只能吸收有限时长的峰值，不能解决长期进入速率大于处理速率。引入 MQ 也不能绕过本方案中任务数据库的入站写入瓶颈；须同步压测存储和扩容。若改成 MQ 为接收事实来源，则需单独重设计幂等、查询一致性和接收确认协议。

验收规划：构造约定规模的突发负载，核对已接收任务数与最终状态；验证超限拒绝、积压消退、供应商隔离和进程故障下的恢复。先定义峰值、持续时间、消息大小和目标处理能力，再给出容量承诺。

## 2. 尽量降低转发耗时

先区分指标：

- 接收耗时：请求进入 API 到持久化确认返回。
- 调度耗时：持久化提交到首次发起外部请求。
- 外部调用耗时：发起请求到收到供应商响应。
- 完成耗时：从接收到最终确认成功；包含重试，不能与首次调度混为一谈。

当前每秒轮询在空闲、到达时间均匀的理想情况下引入约 0–1 秒等待，平均约 0.5 秒；积压、数据库争用和供应商延迟会继续增加耗时。

- [ ] **先测 P50/P95/P99**：分别记录上述阶段，不用平均值掩盖尾延迟。
- [ ] **提交后唤醒**：数据库事务成功后通知 Worker 立即领取；唤醒信号只是提示，任务仍以数据库为准。必须保留定期扫描，覆盖通知丢失及进程重启。
- [ ] **可靠事件分发**：多机时评估 Outbox + MQ 消费推送/长轮询，降低固定轮询等待。Outbox 自身也需要低延迟发布或 CDC，否则只是把轮询延迟搬到另一层。
- [ ] **到期任务调度**：按最早 next_attempt_at 安排唤醒；内存定时器用于加速，持久化时间用于重启恢复。避免用每条消息长时间 sleep 占住执行槽位。
- [ ] **复用连接**：复用 HTTP 客户端与连接池，控制连接数和超时，减少重复建立 TCP/TLS 连接；先测量再调整，不能无限加并发。
- [ ] **减少关键路径工作**：接收路径只做必要校验和持久化；日志和统计避免阻塞。不要为了低延迟先返回成功再落盘。
- [ ] **优先级与公平性**：必要时给紧急通知独立队列或权重，限制普通消息饥饿；有序分组内不能凭优先级跨越前序消息。

权衡：缩短轮询间隔是简单优化，但会增加数据库负载；推送机制增加组件复杂度。批处理提高吞吐可能增加单条延迟。服务只能优化自身等待，不能保证供应商响应速度。

验收规划：比较轮询与唤醒方案在空闲和高负载下的调度 P99；主动丢弃唤醒信号，验证兜底扫描仍能处理任务。

## 3. 一致性、持久性与防丢失

不能只用“消息队列可靠”替代端到端设计。需要逐段明确谁已经接收责任、什么时候确认，以及失败后由谁重试。

| 链路 | 可能出现的问题 | 后续措施 |
|---|---|---|
| 业务事务 → 通知请求 | 业务提交成功，但进程在通知前退出 | 业务方将业务数据与 Outbox 事件同事务提交，再可靠转发 |
| 调用方 → API | 接收成功响应丢失，调用方不确定是否入库 | 稳定事件 ID、调用方级幂等唯一约束、原键重试和状态查询 |
| API → 数据库 | 内存中确认、未提交、主机或存储故障 | 持久化提交后才确认；明确同步写入配置、复制策略和故障保障范围 |
| 任务库 → MQ | 写库成功但消息未发出，或消息已发出但未记录 | 同事务任务表 + Outbox；发布确认后标记已发布；允许重复发布，消费去重 |
| MQ → Worker | Worker 收到后崩溃、过早 ACK | 在持久化记录处理结果或下一次调度责任后再 ACK；重复通知按任务状态过滤 |
| Worker → 供应商 | 对方已经执行但响应丢失 | 供应商幂等、权威结果查询或事务协议；发送端数据库无法单独解决 |
| 终态记录与运营 | 任务被过早删除、失败无人处理 | 失败隔离、告警、对账、受控重放、保留策略和审计 |

- [ ] **明确消息身份**：区分稳定业务事件 ID、任务 ID 和尝试 ID；幂等键按可信调用方身份隔离。
- [ ] **明确事实来源**：采用任务库为主时，数据库决定状态，MQ 只携带分发信息。等待重试的任务必须有可靠的到期调度器，不能 ACK 后只剩一个内存定时器。
- [ ] **配置 MQ 可靠性**：按选定产品配置持久化、复制、发布确认和手动消费确认；检查不可路由消息，确认入队不代表供应商已完成处理。
- [ ] **恢复与对账**：扫描未发布 Outbox、过期 processing、到期未执行任务和失败任务，修复状态停滞；恢复操作保持幂等。
- [ ] **高可用与备份**：明确同步/异步复制、故障转移和备份恢复策略，演练恢复。异步复制可能丢失已确认尾部写入，备份也不能代替实时持久化。
- [ ] **定义 RPO/RTO**：约定允许丢失多少数据、允许恢复多久；只有在明确故障模型和存储条件下才能承诺数据不丢。
- [ ] **故障注入验收**：在事务提交前后、发布确认前后、HTTP 返回前后强制中断；核对每个已接收任务最终可追踪，重复与结果未知被明确记录。

边界：任务记录不丢失、HTTP 成功送达、供应商业务恰好执行一次是不同承诺。永久目标故障不能保证送达；全副本损毁超出既定容灾范围时不能承诺绝对零丢失。

## 4. 有序消息和只能投递一次的消息

### 4.1 有序消息

首先约定顺序含义：接收顺序、发起请求顺序，还是供应商业务生效顺序。HTTP 202/2xx 只表示相应 HTTP 契约下的接收，未必代表异步业务已经完成。

- [ ] **业务分组有序**：增加拟议的 ordering_key，例如订单 ID；同组串行，不同组并行。通常不要求全部通知全局串行。
- [ ] **确定序号来源**：增加拟议的 sequence；若要求业务发生顺序，由业务事务生成序号。不能用网络到达时间或各进程本地时间替代业务顺序。
- [ ] **同组唯一执行权**：同组路由到同一分区/调度通道，同时以持久化组游标控制下一条资格；不能仅假设 FIFO 队列就保证完成顺序。
- [ ] **前序失败阻塞后序**：严格顺序下，前一条重试期间后一条不得绕行；前一条最终失败则暂停该组并告警。
- [ ] **明确缺号、重复与跳过**：缺号等待并对账；重复序号校验内容；人工跳过必须审计，并明确放弃该处严格顺序保证。
- [ ] **控制切换与迟到请求**：消费者切换时防止旧执行者继续发出后续请求。发送端租约只能约束本地状态；严格业务生效顺序仍需接收端按序号校验、去重或提供完成确认。

验收规划：让组 A 第一条超时，验证 A 第二条阻塞、组 B 仍可运行；测试缺号、重复、消费者切换和重启。若供应商异步执行且不支持顺序协议，只承诺约定范围内的发送顺序，不承诺业务完成顺序。

### 4.2 只能投递一次，且供应商不保证幂等

必须区分两种需求：

| 需求 | 可行方案 | 代价或前提 |
|---|---|---|
| 最多发起一次请求，允许可能未送达 | 持久化消费一次发送资格，再发 HTTP；任何结果不确定都不自动重发 | 发送前崩溃可能一次都没发；无法同时承诺必达 |
| 必须成功且业务恰好执行一次 | 接收端原子去重与业务更新，或支持可靠事务/操作 ID 协议 | 需要接收方配合，通用 HTTP 发送端无法独自保证 |

- [ ] **按消息配置投递策略**：未来可区分 retryable 与 single_attempt；字段仅为候选，不加入当前 API。
- [ ] **单次资格原子消费**：single_attempt 任务在网络请求前持久化不可再次领取的标记；只有首次成功获得资格的执行者可以发送。重复队列通知和进程恢复均不能恢复资格。
- [ ] **禁止隐式重试**：该模式下禁用客户端、代理和应用层的请求级自动重试及重定向；不能只把重试次数改为 1 就认为所有路径都满足。
- [ ] **保存结果未知**：超时或发送阶段中断后标记 unknown，不标成“确定未执行”；禁止常规人工重放工具对其再次投递。
- [ ] **供应商协作方案**：优先要求稳定 operation_id；供应商将去重记录与业务副作用原子提交并返回已有结果。单独放一个代理去重仍不能消除代理调用供应商后的崩溃窗口。
- [ ] **结果核查**：若供应商提供权威操作查询，可核查已有结果；“暂时查不到”不等于旧请求不会随后执行，只有协议明确排除在途执行时才能安全决定重发。

关键故障窗口：

```text
先记已发送，再发 HTTP：中间退出 → 可能漏发。
先发 HTTP，再记已发送：中间退出 → 恢复重发可能重复。
```

因此，对不支持幂等、事务或可靠查询协议的外部 API，不能同时保证“不丢、必达、绝不重复执行”。MQ 的 exactly-once 能力不会自动覆盖这个外部 HTTP 副作用。

### 4.3 有序与单次模式组合

- 同组消息 single_attempt 出现 unknown 时，应暂停组并核查；继续发送后序可能使业务状态越序。
- 业务若允许跳过未确认消息，应把它写成显式契约并审计，不能继续声称严格完整顺序。
- 全局顺序、极低延迟、无限吞吐与绝不重复并非可以无代价同时满足的目标，需按消息类别约定优先级。

## 5. 建议推进顺序

1. 明确容量、延迟指标、顺序定义、单次投递可否漏发和 RPO/RTO。
2. 增加观测、背压、供应商隔离、持久化配置及恢复演练。
3. 根据测量结果引入提交后唤醒；有实际瓶颈再迁移数据库、增加 Worker 或 MQ。
4. 有真实业务需要时引入分组顺序与 single_attempt，并先签订供应商侧能力契约。

以上均为后续候选事项，不纳入当前 MVP 实现。

- [RabbitMQ 确认机制](https://www.rabbitmq.com/docs/confirms)：发布确认与消费确认属于不同责任边界。
